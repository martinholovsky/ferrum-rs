# AGENTS.md — working in the Corten repository

Instructions for AI coding agents (Claude Code, Codex, Cursor, Copilot and others) and for humans who want the same ground rules. `CLAUDE.md` points here; this file is the single source.

## What this repository is

Corten is a hardened Rust profile that aims to make whole classes of security bugs impossible to write and the rest mechanically checkable. Today it is mostly design: [`docs/spec.md`](docs/spec.md) is the design, [`docs/rust-comparison.md`](docs/rust-comparison.md) compares it with plain Rust, and [`ledger/cwe-ledger.csv`](ledger/cwe-ledger.csv) holds one row per MITRE CWE weakness. The code: [`crates/cargo-corten`](crates/cargo-corten) (`cargo corten check` and the hermetic `build`, the profile and dependency policy), [`crates/corten-std`](crates/corten-std) (the Phase 2 prelude), [`crates/corten-runtime`](crates/corten-runtime), [`crates/corten-broker`](crates/corten-broker) and [`crates/corten-sandbox`](crates/corten-sandbox) (Phase 3 supervision, brokers and the Landlock launcher), [`crates/corten-ledger`](crates/corten-ledger) and [`crates/corten-corpus`](crates/corten-corpus) (the gates) and [`corpus/`](corpus) (compile-fail cases). Read the README first, then the spec section your task touches.

## Rules that are specific to Corten

1. **An E claim needs a failing build, not an argument.** A CWE may be marked E (eliminated by construction) only when a compile-fail test shows a program exhibiting the weakness does not build, and a matched benign program does build. Record the test in the ledger's `proof_test` column. Until then the row stays `unverified`. Only `corten-corpus --mark-verified` sets `verified`; never edit the status by hand. A row with `review = required` (an encoder in `corten-std`) cannot be verified until an independent reviewer, not the encoder's author, records a review link in that column. Every way of writing the weakness you find goes into the case as another `bad-*.rs`, detected or not (corpus/README.md).
2. **Report the false-rejection rate beside every detection number.** A rule that catches bad code but also rejects good code is not done. Every result states both: how many bad programs failed to build, and how many good programs failed too, with the totals.
3. **The checker supplies its own configuration.** `cargo corten check` must inject its flags (for example `-F unsafe_code`) and lint lists itself. Never read them from the repository being checked: an author can delete an in-source `#![forbid]` and the crate builds again (measured, spec section 10).
4. **Do not move a CWE between buckets without a reason in the ledger.** Bucket changes go through the ledger with the mechanism and, for disputed ids, a response to the reasons in `dispute_reasons`. The 14 ids disputed by two or more panel members (spec section 6) are decided first.
5. **Respect the owner's decisions.** The nine questions in spec section 8 were decided on 2026-10-26 (panel position kept on all nine). Reopening one is an owner decision; ask. New open questions go in section 8 as Open, and the same rule applies to them.
6. **Rust applicability comes from the audit.** Whether a CWE can be written in Rust, in safe Rust, or not at all is decided in `audit/applicability/`: a reviewed row with reasoning, and a program wherever the compiler decides. Change a verdict there, with its program, and run `scripts/applicability-table.py`; it writes the table, `docs/rust-applicability.md` and the counts, and refuses when a verdict, a program and the ledger's `rust_applicability` disagree. Never edit the generated files or that ledger column by hand.
7. **Every CWE that safe Rust can still write under Corten names a mitigation strategy.** The ledger's `strategy` column holds one of the ids in `audit/residual/strategies.csv` (spec section 8, question 15; [`docs/residual-mitigation.md`](docs/residual-mitigation.md)). `corten-ledger check` requires it on every such row and refuses it on a CWE safe Rust cannot write. After changing a strategy, or a row's bucket, status or applicability, run `scripts/residual-map.py` to regenerate `docs/residual-cwes.md`; CI fails when it is stale.
8. **Numbers come from the ledger.** Bucket totals and counts in the docs are the output of `cargo run -p corten-ledger -- totals`, pasted, never edited by hand. `corten-ledger check` must pass (it runs in CI).
9. **Names.** The project is Corten. Crates and tools are `cargo-corten`, `corten-std` and `corten-*`. The bare `corten` crate name on crates.io belongs to someone else.
10. **Keep the CWE notice intact.** Any copy of CWE names or identifiers keeps MITRE's copyright line and terms (`ledger/NOTICE`).
11. **The design panel's transcript is not public.** Do not ask for it or try to reconstruct it; the spec and the ledger (including `dispute_reasons`) are the public record.

## General working rules

- **Validate before you assert.** Check claims about code, versions, tools and external facts against a primary source (read the file, run the command, fetch the official docs) before stating them, and label anything unverified.
- **Keep docs current in the same change.** When behaviour, rules or the ledger change, update the spec, README and this file in the same commit.
- **Prove a check can fail before trusting it passed.** A scan or test that reports "nothing found" counts only if the same instrument finds a planted positive (for example, gitleaks finding a planted token).
- **Gates.** Pre-commit (`.pre-commit-config.yaml`, generated by the SOTA `init-gates.sh`) runs gitleaks and `cargo fmt --check` on commit, and clippy `-D warnings`, `cargo test` and `cargo audit` on push; install hooks with `pre-commit install --hook-type pre-commit --hook-type pre-push`. CI (`.github/workflows/ci.yml`) runs fmt, clippy, rustdoc, nextest, doctests, the ledger gate, the applicability evidence and the generated docs (`docs/rust-applicability.md`, `docs/rust-comparison.md`, `docs/residual-cwes.md` and the chart must be what their scripts generate), the corpus, `scripts/hermetic-smoke.sh`, the Action self-test, the lint driver's fmt, Clippy and UI tests on its pinned nightly, `cargo deny` and gitleaks. Actions are pinned by commit SHA.
- **Run Linux checks in a container before pushing.** Much of the code is `cfg(target_os = "linux")` (`openat2`, Landlock, the broker tests), so macOS Clippy and tests do not see it. Run clippy, the tests and the smoke test in `podman run -v "$PWD":/src -w /src -e CARGO_TARGET_DIR=/tmp/target docker.io/library/rust:1.99.1-slim-bookworm` (add `clippy` with rustup and `python3` with apt). Build the whole workspace before running `cargo-corten`'s tests there: on Linux `cargo corten check` needs `corten-sandbox` beside it, and refuses without it. In a shell that leaks descriptors, run through `scripts/close-leaked-fds.sh`, or the sandbox refuses to start.
- **The lint driver (`crates/corten-lints`) is outside the workspace** and builds on the nightly its own `rust-toolchain.toml` pins: run `cargo build`, `cargo test` and `cargo clippy` from that directory (in the container on Linux). The checker requires it, so run `scripts/build-driver.sh` before the workspace tests; they find it there or through `CORTEN_DRIVER`. In a container that shares the checkout, set `CORTEN_LINTS_TARGET_DIR` (for example `/tmp/lt`), or the Linux build overwrites the host's binary. The nightly's rustc API changes between releases; read its source under `$(rustc --print sysroot)/lib/rustlib/rustc-src` rather than guessing.
- **`main` is protected** by a repository ruleset (`main`, no bypass, admins included): changes land only through a pull request with the five CI checks green on an up-to-date branch (`fmt, clippy, doc`, `tests`, `lint driver (nightly)`, `cargo deny`, `gitleaks`, each pinned to GitHub Actions; the lint driver required since 2026-11-01, owner decision, because the checker requires the driver); no force-push, no deletion, linear history, rebase or squash merges. No approval is required: the sole maintainer cannot approve their own pull requests. `.github/CODEOWNERS` requests the maintainer's review on every pull request. Signed commits are **not** required (owner decision, 2026-10-30): GitHub cannot sign a rebase merge, so the rule would allow squash merges only. **Releases are signed instead:** every release is a tag signed with the maintainer's OpenPGP key (`git tag -s`), held on a hardware key. No ruleset enforces that yet, and nothing is released yet.
- **`corten-std` passes its own profile.** No `unsafe`, no unchecked arithmetic, no banned `std` API; the corpus builds it under `cargo corten check` on every run. A dependency it needs must offer a safe API (see the `region` and `rustix` choices in docs/tcb.md).
- **Workspace conventions.** Edition 2024, toolchain pinned in `rust-toolchain.toml`, lints in the workspace `Cargo.toml` (`unsafe_code = "forbid"`, no `unwrap`/`expect`/`panic` outside tests, `#[expect]` with a reason instead of `#[allow]`). `cargo-corten` has no dependencies on purpose: it is part of the trusted base. Adding one needs a reason and must pass `deny.toml`.
- **A test of a hostile configuration needs a control.** Show the configuration bypasses plain cargo before showing the checker stops it, and run cargo from the fixture's directory: cargo reads `.cargo/config.toml` from the working directory, not from `--manifest-path`.
